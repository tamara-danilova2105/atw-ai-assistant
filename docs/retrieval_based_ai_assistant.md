# Retrieval-based логика AI-консультанта

## Статус

Proposed

---

## Контекст

AI-консультант не должен отвечать только на основе генеративной модели.  
Для продуктового сценария подбора туров важны актуальные данные: доступные даты, цены, длительность, наличие мест и условия тура.

Поэтому первая версия ассистента строится как retrieval-based система:

```text
пользовательский запрос
→ извлечение фильтров
→ поиск по реальным данным
→ подготовка найденного контекста
→ генерация ответа
```

---

## Решение

Используется retrieval-first подход.

LLM не является источником правды.  
Модель подключается после того, как система уже нашла релевантные данные.

```text
User message
→ FilterExtractor
→ SearchFilters
→ Retrieval layer
→ Matched tours
→ Context builder
→ LLM answer
```

---

## Почему не сразу LLM

Плохой вариант:

```text
User message
→ LLM
→ Answer
```

Проблемы такого подхода:

- модель может придумать несуществующий тур;
- может ошибиться в цене;
- может назвать неверные даты;
- может не учитывать наличие мест;
- сложно контролировать качество ответа;
- невозможно гарантировать актуальность данных.

---

## Retrieval-based подход

Правильный flow:

```text
User message
→ Structured filters
→ Database search
→ Real matched data
→ LLM explanation
```

Сначала система получает факты из базы данных.  
Только после этого LLM формирует человекочитаемый ответ.

---

## Роль FilterExtractor

`FilterExtractor` преобразует естественный язык в структурированные параметры поиска.

Пример:

```text
Хочу тур в Дагестан в июле до 80000 на 5 дней
```

Результат:

```python
SearchFilters(
    region="Дагестан",
    month=7,
    max_price=80000,
    days_count=5,
)
```

На первом этапе extraction может быть rule-based.  
Позже его можно заменить или усилить LLM-based structured extraction.

---

## Роль SearchFilters

`SearchFilters` — это промежуточный контракт между пользовательским текстом и системой поиска.

Он не является сущностью базы данных.

```python
class SearchFilters(BaseModel):
    region: str | None = None
    direction: str | None = None
    month: int | None = None
    year: int | None = None
    max_price: int | None = None
    days_count: int | None = None
    activity: str | None = None
    comfort: str | None = None
```

---

## Роль adapter layer

Ассистентские фильтры и фильтры каталога могут иметь разный формат.

Пример assistant filters:

```python
SearchFilters(
    region="Дагестан",
    month=7,
    max_price=80000,
    days_count=5,
)
```

Пример catalog filters:

```python
CatalogFilters(
    region=["Дагестан"],
    price=[0, 80000],
    duration=[5, 5],
    dates={
        "startDate": "2026-07-01",
        "endDate": "2026-07-31",
    },
)
```

Adapter изолирует преобразование форматов и не даёт AI-слою зависеть от деталей каталога.

---

## Роль retrieval layer

Retrieval layer отвечает за поиск релевантных данных.

Он выполняет:

- фильтрацию по параметрам;
- поиск по базе данных;
- ограничение количества результатов;
- возврат только реальных найденных объектов;
- подготовку данных для следующего слоя.

На этом этапе система ещё не “думает” как AI.  
Она гарантирует, что дальнейший ответ будет основан на реальных данных.

---

## Роль ContextBuilder

`ContextBuilder` нужен для подготовки данных к передаче в LLM.

Он не передаёт модели весь сырой объект из базы.  
Вместо этого он собирает компактный контекст:

```text
Тур: Дагестан. Все топ локации за 5 дней
Регион: Дагестан
Дата: 8–12 июля 2026
Цена: 60000 ₽
Длительность: 5 дней
Включено: проживание, трансфер, питание, гид
```

Это снижает шум и уменьшает риск некорректного ответа.

---

## Роль LLM

LLM отвечает не за поиск данных, а за формулировку ответа.

Задачи LLM:

- объяснить, почему тур подходит;
- сравнить несколько вариантов;
- сформулировать ответ естественным языком;
- задать уточняющий вопрос;
- не выходить за пределы переданного контекста.

---

## Архитектурная граница

```text
Retrieval layer = источник фактов
LLM layer = слой объяснения и диалога
```

Такой подход разделяет:

- поиск данных;
- бизнес-логику;
- подготовку контекста;
- генерацию ответа.

---

## Преимущества подхода

Retrieval-based архитектура даёт:

- контроль над источником данных;
- защиту от hallucinations;
- переиспользование существующего каталога;
- возможность тестировать поиск без LLM;
- прозрачную отладку;
- основу для semantic search;
- основу для recommendation engine;
- возможность подключить разные LLM без переписывания бизнес-логики.

---

## Текущее состояние

На текущем этапе реализован retrieval foundation:

```text
message
→ filters
→ catalog filters
→ DB search
→ matched tours
→ structured response
```

Это ещё не полноценный AI-консультант, но это обязательная основа для production-oriented AI-системы.

---

## Следующий этап

Следующий этап:

```text
matched tours
→ TourContextBuilder
→ LLMService
→ conversational answer
```

После этого ассистент сможет не только находить туры, но и объяснять рекомендации в формате живого диалога.

---

## Итог

Retrieval-based подход нужен для того, чтобы AI-консультант отвечал не “из головы модели”, а на основе актуальных данных системы.

Главный принцип:

```text
Сначала факты из базы данных.
Потом LLM-ответ на основе этих фактов.
```
